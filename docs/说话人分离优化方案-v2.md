# 说话人分离优化方案 v2

> 背景：实时层（VAD 切段 + 逐段声纹匹配/在线质心聚类）在"连续接话"场景下
> 会把多人合并为一人。本文档调研现成开源方案，给出渐进式升级路径。
> 日期：2026-09-05

## 1. 现状梳理：每个模型干什么

| 模块 | 模型 | 职责 | 输出 |
|------|------|------|------|
| VAD | FSMN-VAD | 切句（静音 350ms / 最长 8s） | speech start/end |
| ASR online | Paraformer-large streaming | 流式临时字幕 | 纯文本（无说话人） |
| ASR offline | Paraformer-large | 段终确定文本 + 词级时间戳 | text + timestamp |
| 标点 | CT-Transformer | 加标点 | punc_array |
| 声纹 | **CAM++** | 段 → 192 维 embedding | spk_embedding 向量 |

关键点：**"谁说的"全部来自 CAM++，ASR 模型本身从不返回说话人**。
服务端拿 CAM++ embedding 做两件事：
1. 与注册声纹库（speaker_db.json）算余弦相似度，> 0.45 出真名；
2. 否则与会话内"滚动质心"聚类，输出 说话人N。

当前缺陷：逐段独立判定 + 短视质心，没有"全局视角"。VAD 段（最长 8s）
仍可能混入多人 → 混合 embedding → 全部归并。

## 2. 商业产品（reccloud 等）为什么强

它们走的是**离线分段-聚类（segmentation-clustering）完整版**：

```
整段音频
  → VAD 去静音
  → 固定滑窗（1~2s，窗够小基本不跨人）
  → 每窗算 embedding（同 CAM++ 类模型）
  → 全局聚类（AHC / spectral，一次性看清全场结构）
  → 输出"谁在第几秒到第几秒说话"
```

与我们实时版的本质差距不在模型，在**算法范式**：全局聚类 > 在线启发式。

## 3. 现成开源方案调研

### 3.1 ModelScope 官方 CAM++ diarization pipeline（首选）

- 地址：`iic/speech_campplus_speaker-diarization_common`（[模型页](https://modelscope.cn/models/iic/speech_campplus_speaker-diarization_common/)）
- **就是我们现有模型的官方组合**：FSMN-VAD + CAM++ + 聚类，外加 CAM++ 说话人转换点定位模型（切边界更准）
- 官方指标：2 人对话 DER 4.7%，2-10 人 DER 8.0%
- 调用：`pipeline(task='speaker-diarization', model=...)(wav, oracle_num=N?)`，输出每段 [start, end, speaker]
- 无授权门槛（ModelScope 直接下载，内网可用），funasr/modelscope gpu 机上已装
- 局限：不处理**同时重叠**说话（分段-聚类范式的固有假设）；<30s 短音频效果差（对我们无影响，我们按分钟窗口跑）

### 3.2 pyannote.audio 3.x（备选基准）

- DER ~11-19%（标准基准），segmentation-3.0 用 powerset 架构可标注重叠段
- 门槛：HF 账号 + 同意 gated license + huggingface 访问（内网不便，需 hf-mirror）
- 适合作为二期对照组：同样输入，和 3.1 比 DER，谁好用谁

### 3.3 3D-Speaker / sherpa-onnx

- 3D-Speaker 新版 diarization 框架 = 分段-聚类 + EEND 双分支，**EEND 负责检测局部重叠**
- sherpa-onnx 提供 `sherpa-onnx-offline-speaker-diarization` 现成二进制，ONNX 化可 CPU 跑
- 可作为三期"重叠说话标注"的载体

### 3.4 阈值推荐（回应"一直在调阈值"）

余弦相似度阈值**没有通用最优值**，随麦克风/房间/人变化，必须实测标定。
经验范围（中文会议、单麦、cam++）：

| 场景 | 建议测试区间 |
|------|------------|
| 同人同麦跨句 | 0.55 ~ 0.75 |
| 跨人同麦 | 0.25 ~ 0.50 |

方法：用 `scripts/diag_spk.py`（相似度矩阵）对真实会议录音扫阈值网格
{0.45, 0.5, 0.55, 0.6, 0.65}，数"同人分散数 + 跨人合并数"，取最小值点。
标定后固化进 `.env`。

## 4. 目标方案：渐进式重标注（实时保持，标签持续修正）

```
实时层（不动）：浏览器实时字幕 + 快速说话人标签（现状，管现场）
        ↓ 音频同时累计落 wav
后台层（新增）：每 30s 对累计 wav 跑一次 3.1 pipeline
        ↓ 输出全局最优说话人分段
修正层（新增）：用 diarization 结果重写已落库 utterance 的 speaker
        ↓ WebSocket 广播刷新
前端（小改）：已显示的句子 speaker 标签就地更新
```

- 会议纪要的主要消费场景是**会后**，1 分钟级延迟完全可接受
- 会议结束时最后一轮重标注，保证存档是全局最优
- 注册声纹库继续生效：pipeline 输出的匿名簇再与注册库比对出真名

### 4.1 改造清单

| # | 位置 | 改动 | 工作量 |
|---|------|------|--------|
| 1 | gpu 服务端 | 新增 WS 控制消息 `{"mode":"diarize"}` + wav 字节 → 返回 speaker 分段 JSON（复用 enroll 控制连接模式） | 半天 |
| 2 | 后端 | 后台 asyncio 任务：会议中每 30s、结束时各跑一次；映射回 utterance（按时间戳重叠对齐）并更新 DB + 广播 | 半天 |
| 3 | gpu 服务端 | offline 消息补 `seg_offset_ms`（段起点在全场中的偏移），让时间戳变全局绝对值 | 2 小时 |
| 4 | 前端 | 逐句转写区收到刷新就更新标签 | 1 小时 |
| 5 | 前端 | **播放高亮**：audio `timeupdate` → 定位当前句 → 高亮+滚动（依赖 #3 的全局时间戳） | 2 小时 |
| 6 | 工具 | diag_spk.py 加阈值扫描，出标定报告 | 2 小时 |

### 4.2 资源评估（用户已确认资源不设限）

- pipeline 全 CPU 可跑：1 分钟窗口 ≈ 滑窗 40~60 个 × CAM++ 推理（每个 <100ms）+ VAD，单次重标注 <10s
- 若上 pyannote：segmentation-3.0 约 1.5GB 显存/下载，建议 GPU 机
- 4090 迁移 FunASR 后（独立事项），实时层延迟同步下降

## 5. 效果预期与边界

| 场景 | 预期 |
|------|------|
| 两人连续接话（有小停顿） | **显著改善**，pipeline DER 个位数百分比，商业产品同水平 |
| 注册声纹的参会人 | 真名标注，叠加后更稳 |
| 两人**同时**重叠说话 | 仍不可分（一期接受，三期考虑 EEND/OSD 至少标出"多人同时说话"） |
| >10 人大会 | 效果下降（pipeline 官方建议 ≤10 人） |

## 6. 里程碑

- M1：#1 #2 跑通 → 真人会议验证"连续接话分人"
- M2：#3 #4 #5 播放高亮 + 标签刷新 → 调试体验质变
- M3：#6 阈值标定 → 固化配置
- M4（可选）：pyannote 对照实验；EEND 重叠标注

# 会议纪要系统 · 工作详细汇报

> 项目：内网私有化部署的**实时会议转写 + 说话人区分 + AI 纪要系统**
> 周期：2026-09-04 ~ 2026-09-08（5 个工作日，28 个代码提交）
> 约束：数据不出内网（死约束）——所有语音、转写、纪要均在本公司 GPU 服务器与内网完成

---

## 一、项目背景与目标

老板最初设想采购录音笔硬件采集会议音频。调研后明确了本质需求：**数据安全**——只要语音不出内网，直接网页/电脑收音即可，录音笔反而引入格式转换、传输链路等额外环节。经与老师对齐，确定先做**电脑直接录音**方案。

最终目标形态：

- 网页端一键开始会议录音，实时转写并区分说话人；
- AI 实时纠错 + 滚动纪要，会末生成标题/总结/标签/事实性属性；
- 历史会议落库可查、录音可回放、纪要可导出；
- 后续可集成进 RuoYi / 泛微 OA（中间层方案已论证）。

## 二、技术架构（已全部落地）

```
浏览器 (Vue3 + WebAudio, PCM 16kHz 流式)
   │ WebSocket
   ▼
FastAPI 后端 ──┬── FunASR 2pass (GPU:10095)   实时转写 + 说话人标签
               ├── diarize 服务 (GPU:10096)   ERes2NetV2 声纹 / 阿里 pipeline
               ├── LLM 网关 (内网 vLLM)        实时纠错 + 滚动纪要 + 会末总结
               │      └── Langfuse 全链路埋点（每次调用输入/输出/耗时/失败可追溯）
               └── SQLite                     会议/句子/纪要落库，录音存盘
```

| 组件 | 技术选型 | 说明 |
|---|---|---|
| 前端 | Vue3 + Vite + Vant | 手机/电脑自适应；HTTPS 解决浏览器麦克风权限 |
| 后端 | Python + FastAPI + WebSocket | 异步全链路，音频 0.1s 粒度流式处理 |
| 转写 | FunASR Paraformer 2pass | 流式出临时字幕，离线出确定句+字级时间戳 |
| 说话人 | ERes2NetV2 声纹（阿里达摩院） | 盲测完胜 CAM++，详见第三节 |
| LLM | 内网 Qwen（LiteLLM 网关） | 纠错/纪要/属性提取；Langfuse 可观测 |
| 数据 | SQLite + 本地 wav | 数据不出内网；录音回放支持 |

## 三、核心难点一：说话人区分——四方盲测选型

说话人区分（diarization）是本系统最核心的难点。我们没有拍脑袋选型，而是**把业界主流方案全部拉到本地 GPU，用同一批真实会议录音（双人对话、单电脑麦克风）做分轨导出 + 人工盲听 + 声纹余弦相似度量化对比**：

| 方案 | 组成 | 盲测结论 |
|---|---|---|
| FunASR + CAM++ | FunASR 自带说话人聚类 | 基线可用，约 50% 区分率，多人连续说话大量混判 |
| 阿里 pipeline + CAM++ | pyannote 式切分 + CAM++ | 明显优于基线，支持 oracle 人数约束 |
| 阿里 pipeline + **ERes2NetV2** | 切分 + 新一代声纹 | **盲听最佳**：连续说话区分准确、错误率可接受 |
| pyannote（国际口碑最强） | 端到端 diarization | **中文场景意外地差**：碎段多、错误率高，远不及阿里 pipeline |

选型结论：**FunASR（转写）+ 阿里 pipeline（切分）+ ERes2NetV2（声纹）**。

配套测试工作量：

- 录音分轨导出、人工盲听打分、声纹相似度量化评估（63 段逐段对照表，一致率 78%，全部留档于 `docs/eval/`）；
- CAM++ vs ERes2NetV2 **同批注册样本公平竞技**（ERes2NetV2 明显胜出，已实际试听验证）；
- 排查并解决 pyannote/HuggingFace 鉴权、GPU 显存占用、服务化封装等工程问题；
- 另评测过 OddASR（流式不分人）、Aham Voice（同路线，无可借鉴点），书面留档。

**关键认知**：在线产品（reccloud 等）是"录完整段再识别"，我们是实时流式——难度高一档，这个差异贯穿了后续全部调优。

## 四、核心难点二：实时滚动管线（自研）

在线产品整段后处理的从容，我们要在 8 秒窗口里兑现。为此自研滚动增强管线：

- **滚动窗口**：有效语音 ≥8s 成窗（不足自动并入下轮，墙钟 15s 强制成窗），窗口音频送 GPU 打说话人标签；
- **重叠纠错**：每轮 LLM 输入 = 上轮原文 + 上轮纠正文 + 本轮原文，**允许原地修正上一轮**（说话人话没说完时先出的纠错，下轮自动修正）；
- **滚动纪要**：纪要不是每 8 秒从零总结，而是"上轮纪要 + 本轮内容"锚定改写，越滚越准；
- **草稿先行**：原始转写以灰色草稿先出（~1s），AI 纠错定稿后原地替换——兼顾实时反馈与最终质量；
- **会末一次性生成**：标题、完整总结、标签、事实性属性（参会人等由 AI 自主提取，不预设字段，给什么渲染什么）。

## 五、排障全记录（16 个坑，全部定位到根因）

> 这部分是工作量的核心体现。以下坑绝大多数**不报错、只表现为"效果差"**，每个都要靠对照实验逼出来。

### A 类：隐性 Bug（代码正确性问题）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 全员误标同一个人 | 声纹 embedding **未归一化**，相似度全部失真 | 归一化（`de76304`） |
| 2 | 滚动打标切错音频、重标注回写 0 句 | 2pass 离线时间戳**没加段绝对偏移** | 偏移修正（`8f50632`） |
| 3 | 会后版文字与时间错位 | 字级时间戳与文字等长含标点，对齐逻辑按不含标点走，每遇标点错位一格 | zip 对齐重写 |
| 4 | 0.47~0.49 的真匹配被拒，连续错标 | 阈值 0.50（v2 遗留）拦真匹配 + 平滑逻辑继承上一句，级联污染 | 阈值 0.30（`d0826ac`） |

### B 类：算法/模型的物理特性（必须认知并绕开）

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| 5 | 连续说话被并成一人 | VAD 默认 800ms 静音判完，正常换气 300-600ms 直接并段 | 激进切分可配置（`ce26f47`） |
| 6 | 识别出"第 3 个人"幻影 | 阿里 pipeline 自动估人数不可靠（实测 0/4 全错）；拍"注册数+1"又拆出假说话人 | oracle 三模式可配（`fa4bef9`） |
| 7 | 重标注匿名标签覆盖实时真名 | 回写无保护 | 回写保护（`3c9e506`） |
| 8 | **同一音频重跑结果不同**（3 次切出 13/8/8 段） | 阿里 pipeline 谱聚类**天然非确定**，固定随机种子无效；簇质心相似度 0.69/0.24 间跳，低于阈值整场坍缩成单说话人 | **v3 方案：彻底弃用阿里切分，改用实时句子边界 + 逐句声纹 argmax**（`9cb810d`），复跑两次 diff 完全一致 |
| 9 | 短句（<1.5s）声纹不稳 | embedding 在碎段上物理不稳 | 最短声纹段配置 + 相邻句平滑 |

### C 类：工程链路（实时系统的脆弱性）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|

| 12 | 实时版/会后版结果互相矛盾 | 双版本混用同一切分 | 彻底分离：实时版/会后版独立展示（`6bb3890`） |

### D 类：配置与可测性（"调参感觉没用"的真相）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 13 | 阈值改来改去"没效果" | 参数**三处漂移**：config=0.30、前端表单=0.50、手动重标回落 config——同一场会两种触发方式参数不同 | **参数唯一化**：config.py 单一数据源 + GET /api/config（`f813e85`） |
| 14 | 无法做对照实验 | 没有重放/重测手段 | 重放测试（历史录音模拟实时开会）+ 重新测试按钮 + 双版本分离（`99231d5` `3737210`） |
| 15 | 评测靠"感觉" | 无量化标准 | **GT 逐句打分脚本**（口述标注入库）+ **声纹打分快捷脚本**（GPU 上一键出任意段的相似度/margin） |
| 16 | 调参必须改代码 | 硬编码散落 | 全配置化：窗口/阈值/LLM/声纹路径全部进 config + .env，前端配置面板可调 |

### 剩余已知问题（诚实陈述）

1. **句内换人**：一句话内中途换人（如「现在[解决了]，对不起」）。已用滑窗验证**可检出**（说话人分数在换人点突变清晰），方案已设计、待实施；
2. **收音质量极限**：远讲/嘈杂段的声纹 embedding 本身"糊"（margin<0.05），程序无解——这是物理极限，只能靠近讲或更好的麦克风。程序层面可做的是 margin 过低时标"不确定"而非硬塞名字。

## 六、可测性建设（本项目的拐点）

排障速度的质变来自三个工具：

1. **重放测试**：历史录音按真实节奏喂进完整实时管线——不用重新说话就能复现任意一场会，参数改动 A/B 对照成为可能；
2. **实时/会后双版本分离**：两条管线独立展示互不污染，谁的错一目了然；
3. **量化评测**：ground truth 逐句打分（当前主测会议 8/8 全对）+ score_seg 一键声纹打分——从"感觉不对"到"margin 0.004"只差一条命令。

**没有这三个工具，前面 16 个坑里至少一半无法定位。**

---

## 七、工作量与难度评估

**做出来不难，做好很难。**

- 基础链路（录音 → 转写 → 展示）一人一周即可打通——事实上我们 1 天就跑通了；
- 但之后的每一步优化都很艰难：
  - **说话人区分**：4 套方案、数十次盲听测试、63 段量化对照，才锁定 ERes2NetV2 组合；实时场景难度再上一档；
  - **16 个坑**：全部"不报错只表现差"，隐性 bug（归一化/时间戳/参数漂移/非确定性）每个都要靠对照实验逼出来；
  - **实时工程**：GPU 服务、LLM 网关每一次抖动都被放大成用户可见故障，逐个做降级/超时/重排；
  - **参数耦合**：VAD、窗口、阈值、纠错范围互相牵连，只能实测迭代——参数唯一化之前，"调参没用"的根因正是三处漂移互相抵消。

量化：**5 个工作日、28 个提交、4 套方案盲测、16 个根因定位、3 个可测性工具、8/8 ground truth 全对（句子级声纹 v3）**。

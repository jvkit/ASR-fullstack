# 降噪方案调研（服务端语音增强）

> 2026-09-17 ｜ 背景：MAXHUB BM22 自带 DSP 降噪实测无效；Chrome 浏览器 RAW 模式
> 绕过 Windows Voice Clarity 增强；浏览器内置 NS 太弱。需在**服务端**自建降噪层
> （非实时批次架构优势：每个 8~15s 块可任意上重量级模型，浏览器零改动）。

## 结论（决赛圈三选一，全部开源、全部 CPU 可跑）

| 方案 | 出品 | 参数量 | 实时因子(CPU) | 降噪质量 | 中文友好 | 风险点 |
|---|---|---|---|---|---|---|
| **GTCRN** | 西工大（中国团队） | 4.8 万（≈RNNoise 级） | 0.07（极快） | DNS 挑战赛头部 | ★★★ 中文资料/部署文章极多，gitcode 有镜像 | 小众，需自测中文会议场景 |
| **DeepFilterNet3** | 德国开源（Rikorose） | 178 万 | 0.19 | PESQ 2.81，碾压 RNNoise(2.34) | ★★ 语言无关（人声 vs 噪声，不学语言） | 训练语料偏英文场景音 |
| **FRCRN**（阿里 ClearerVoice-Studio） | 达摩院通义 | 较大 | 中等 | 稳态噪声"几乎完全消除" | ★★★ ModelScope 有"单麦 16k"现成镜像，和我们的规格严丝合缝 | ⚠️ **GitHub issue #129：有人反馈 FRCRN 增强后接 FunASR 识别变差** |

## 关键情报

1. **浏览器路线已排除**：Chrome 以 RAW 模式采集，系统级增强（Voice Clarity）进不来；
   Chrome 自带 NS 已开（web/src/ws/audio.ts:22）但算法太老。RNNoise WASM 可作客户端
   备选，但服务端方案质量上限更高、浏览器零改动，优先服务端。
2. **FunASR 兼容性是第一验收项**：我们的转写就是 FunASR 系（SeACo Paraformer），
   FRCRN 已有"增强后识别变差"的前科（github.com/modelscope/ClearerVoice-Studio
   issues/129），所有候选必须过 CER 回归测试，降噪强 ≠ 转写准。
3. **声纹向量兼容性是第二验收项**：ERes2NetV2 认人靠音色，增强引入的语音失真可能
   拉低相似度/拉近不同人向量。DER 对比同测。
4. **会议场景噪声特性**：稳态噪声（空调/风扇/电流）三者都能压；真正难的是突发噪声
   （翻纸/咳嗽/碰杯）和双人同时说话——后者任何单麦降噪都会伤，验收测试必须包含。
5. 中科院声学所 IACAS 团队拿过微软 DNS 挑战赛冠军（2021），中文社区在该领域
   积累深厚，选型不必迷信海外项目。

## 验收协议（沿用 MAXHUB A/B 设计）

同一段带噪录音（含：安静底噪段 / 单人说话 / 双人快速交替 / 停顿后再说话）：
- 三路并行：原始 / GTCRN / DeepFilterNet3 / FRCRN → 重放管线
- 指标：CER、DER、双人段两句话是否都存活、句首字裁剪情况、主观听感
- 判定：CER 不劣化（±2% 以内）且 DER 不降 → 降噪增益才算真增益

## 落选记录

- RNNoise：质量垫底（PESQ 2.34），只作客户端应急备选。
- WebRTC NS（浏览器内置）：已启用，聊胜于无。
- DTLN/NSNet2/DCCRN：质量介于中间，无突出优势，不进决赛。
- 商业方案（Krisp 等）：闭源+按量付费，违背"可归因黑盒"原则，不考虑。

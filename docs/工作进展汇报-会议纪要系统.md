# 会议纪要系统 · 工作进展汇报


> 目标：内网私有化部署的实时会议转写 + 说话人区分 + AI 纪要系统（数据不出内网）

---

## 一、目标与约束

- **数据安全是死约束**：所有语音、转写、总结均在公司内网完成，不依赖任何云服务（这也是自研而非直接用腾讯元宝等在线产品的根本原因）。
- **核心能力**：实时转写、说话人区分（谁在说话）、AI 实时纠错与滚动纪要、会末标题/总结/标签。
- **交付形态**：Web 端（Vue3 + FastAPI），后续可集成进 RuoYi / 泛微 OA。

---

## 二、已完成的工作

### 1. 基础链路搭建（全栈）

- **后端**（Python / FastAPI）：WebSocket 接收前端实时音频流 → FunASR 2pass 实时转写 → 说话人标注 → LLM 纠错/总结 → 落库（SQLite）。
- **前端**（Vue3 + Vite）：网页端录音（WebAudio + PCM 流式上行）、实时转写展示、滚动纪要、历史会议列表、录音回放、声纹注册入口；已适配手机端访问。
- **GPU 服务器**：部署 FunASR（实时转写）+ 阿里 ModelScope 说话人分离 pipeline（说话人切分 + ERes2NetV2 声纹向量），通过独立 HTTP 服务暴露。
- **LLM 网关**：接入公司内网模型（经 LiteLLM 网关），Langfuse 全链路埋点（每次调用的输入/输出/耗时/失败可追溯）。
- 全流程已打通：网页录音 → 实时字幕（带说话人标签）→ AI 纠错 → 滚动纪要 → 会末总结/属性提取 → 历史回放。

### 2. 算法选型：多方案对比测试（工作量最大的部分）

说话人区分（diarization）是本系统的核心难点。我们没有拍脑袋选型，而是**把业界主流方案全部拉到本地，用同一批真实会议录音做盲听对比测试**：

| 方案 | 组成 | 结论 |
|---|---|---|
| FunASR + CAM++ | FunASR 自带说话人聚类 | 基线可用，区分准确率约 50%，多人连续说话时大量混判 |
| 阿里 ModelScope pipeline + CAM++ | pyannote 式切分 + CAM++ 聚类 | 明显优于基线，支持 oracle 人数约束 |
| 阿里 pipeline + **ERes2NetV2** | 切分 + 新一代声纹模型 | **盲听测试最佳**，连续说话区分准确、错误率可接受 |
| pyannote（国际口碑最强） | 端到端 diarization | 中文场景表现意外地差，碎段多、错误率高，远不及阿里 pipeline |

选型结论：**FunASR（转写）+ 阿里 pipeline（说话人切分）+ ERes2NetV2（声纹聚类）**。

对比测试过程包括：录音分轨导出、人工盲听打分、声纹余弦相似度量化评估、多模型声纹库建库（CAM++ vs ERes2NetV2 同批样本对比，ERes2NetV2 明显胜出，已实际试听验证）。过程中还排查并解决了 pyannote/HuggingFace 的鉴权、显存占用、服务化封装等一系列工程问题。

### 3. 实时增强管线（自研，正在迭代）

在线产品是"录完整段再识别"，我们是**实时流式**，难度高一档。为此设计了滚动增强管线：

- **滚动窗口**：有效语音 ≥8s 成窗（不足自动并入下轮，墙钟 15s 强制成窗），窗口音频送 GPU 打说话人标签；
- **重叠纠错**：每轮 LLM 输入 = 上轮原文 + 上轮纠正文 + 本轮原文，**允许原地修正上一轮**（说话人话没说完时先出的纠错，下轮自动修正）；
- **滚动纪要**：纪要不是每 8 秒从零总结，而是"上轮纪要 + 本轮内容"锚定改写，越滚越准；
- **草稿先行展示**（前端）：原始转写以灰色草稿样式先出（~1s 延迟），AI 纠错定稿后原地替换为正式样式——兼顾实时反馈与最终质量；
- **会末一次性生成**：标题、完整总结、标签、事实性属性（参会人等由 AI 自主提取，不预设字段）。

### 4. 配套能力

- **声纹注册**：指定说话人可注册声纹（系统内已建 ERes2NetV2 声纹库），识别结果可落成真名而非"说话人1/2"。
- **oracle 人数**：支持传入已知参会人数，强制约束说话人数量（实测可显著减少"第 3 个人"幻影）。
- **热词**：内建 377 条会议高频词表，提升专名识别。
- **全配置化**：窗口阈值、LLM 模型、总结触发、声纹路径等全部进配置文件/环境变量，调参不改代码。

## 三、近期遇到的问题与定位（体现难度的部分）

上周真机多人实测暴露了一批问题，逐一排查后**根因全部定位**，典型的排障链条如下：

1. **"30 秒等不到修正"** → 不是阈值问题：阿里 pipeline 有硬断言（有效语音须 >5 秒），首轮滚动窗口墙钟 6 秒、扣掉开头静音必然不满足 → GPU 端 500；打标失败后链路继续走 LLM 纠错，恰好赶上内网 LLM 网关故障，SDK 默认重试机制让单个任务卡死 6 分钟，防重入锁又把后续所有轮次挡住 → 整条增强链路瘫痪。
2. **"会议结束 15 分钟还显示进行中"** → 结束流程是串行的：等转写关闭 → 等 LLM 总结（重试 6 分钟）→ 属性提取（又重试 6 分钟）→ 才落库。已设计改为：结束瞬间落库 + 广播，重活全部转后台。
3. **"识别不准/区分不准"** → 本质是上面两条链路全瘫后，展示的是**裸 FunASR 基线**而非完整管线效果，需要修复链路后再评判。

对应的修复方案已全部设计完成并进入实施：有效语音成窗（根治 5 秒断言问题）、LLM 去重试 + 超时兜底（根治卡死排队）、结束流程重排（根治"进行中"假象）、纠错失败自动滚入下轮补纠（LLM 恢复后无需人工干预）。

## 四、工作量与难度评估

**做出来不难，做好很难。**

- 基础链路（录音 → 转写 → 展示）一人一周即可打通，事实上我们也确实很快跑通了；
- 但之后的每一步优化都很艰难：
  - **说话人区分**：试了 4 套方案、数十次盲听测试，才锁定 ERes2NetV2 + 阿里 pipeline 组合；实时场景比离线场景难度再上一档（在线产品都是整段后处理，我们是流式）；
  - **管线工程**：实时系统里每一个外部依赖（GPU 服务、LLM 网关）的抖动都会被放大成用户可见的故障，需要逐个做降级、超时、重排设计；
  - **效果调优**：窗口长度、重叠策略、纠错范围、纪要更新频率，每个参数都互相耦合，只能实测迭代。

## 五、下一步计划

1. 落地本轮 4 项修复（有效语音成窗 / LLM 超时治理 / 结束流程重排 / 失败自动补纠）+ e2e 回归验证；
2. 前端"草稿先行"展示样式上线；
3. 多人多轮真机实测，用真实会议持续校准窗口与阈值参数；
4. 后续：RuoYi 单点登录集成（中间层方案已论证）、声纹注册流程产品化、必要时换更强的内网 LLM 提升纠错质量。

## 一、系统长什么样

系统分**两台机器**协作：

```
┌────────────────────── 本地开发机 (192.168.30.81) ──────────────────────┐
│                                                                        │
│  浏览器 (Vue3 前端 :5174, https)                                        │
│    │  WebSocket 上行: PCM 16k 音频帧        下行: 转写/纪要/状态          │
│    ▼                                                                   │
│  后端 FastAPI (:8010, server/app/)                                      │
│    ├─ api/        meetings / speakers / ws(音频与推送)                   │
│    ├─ core/session.py    会议会话: 攒批调度、批次执行、会末终版           │
│    ├─ core/gpu_pipeline.py  GPU 服务的 HTTP 客户端                      │
│    ├─ core/enhancer.py   LLM 增强: 纠错 + 修正上轮 + 滚动纪要           │
│    ├─ core/reannotate.py 会末/手动全场重标注                             │
│    ├─ llm/        client (OpenAI 兼容) + prompts (提示词模板)           │
│    ├─ db/         SQLite (meeting.db): 会议/句子/说话人                 │
│    └─ config.py   全部可调参数 (从项目根 .env 加载)                     │
│                                                                        │
└──────────────┬─────────────────────────────────────────┬───────────────┘
               │ HTTP :10096                               │ OpenAI 兼容 API
               ▼                                           ▼
┌────── GPU 服务器 (192.168.30.87, ssh gpu) ───────┐   ┌── LLM 网关 (127.0.0.1:4000)
│ diarize_svc (FastAPI :10096)                     │   │   内网 mymodule / vLLM 池
│   /meeting_chunk  VAD切句+ASR+认人(核心)          │   └── Langfuse (localhost:3000,
│   /vad            句尾切点(攒批用)                │       可选, llm 调用追踪)
│   /diarize_sent   给定句子边界逐句认人            │
│   /embed          声纹嵌入                        │
│  FunASR (:10095, websocket) 仅声纹注册管理        │
└──────────────────────────────────────────────────┘
```

一句话概括分工：**本地后端是"调度中枢 + 状态管理 + LLM 编排"，GPU 是"音频理解引擎"，LLM 网关是"文字润色与纪要大脑"**。前端只跟本地后端说话，永远不直连 GPU。

## 二、为什么是这么个架构（30 秒历史课）

这个项目踩过的最大的坑是"实时"。最早的版本是流式 ASR + 声纹投票，想边录边出结果——实测**人一多、话一重叠，实时版错得没法看**（DER 50%+，说话人坍缩成一个人）。结论是：分人这件事必须让模型看到"足够长的上下文"，流式碎片输入天然吃亏。于是 2026-09-13 在分支 `nonrealtime-clean` 上把实时路径整个砍掉，定下现在的**非实时批次架构**：录的时候音频照常实时上传，但识别按"攒够一批再整批送 GPU"的方式做，牺牲几秒延迟换正确率。成绩（aishell4 远场会议基准，注册段同会议抽取的最优情形）：

| 会议 | DER | 主要错误来源 |
|---|---|---|
| S 超市会 (5人) | 5.7% | VAD 漏检 6s + 噪音误报 8s |
| M 幼儿园会 (6人) | 17.2% | VAD 远场漏检 43s |
| L 大会 (7人) | 14.2% | VAD 漏检 30s + 混淆 5s |

**分人混淆已全部压到 2% 以下，剩下的主战场是远场收音质量（VAD 漏检），不是算法。** 这也是"要硬件录音笔"论点的技术依据。

## 三、本地部分详解

### 3.1 数据流：一帧音频的旅程

```
麦克风 ──PCM 16k/16bit──► ws 上行 ──► session.handle_audio() 入缓冲
                                        │
                              _batch_loop() 每 4s 检查一次:
                                缓冲 ≥ 8s 且遇到 VAD 句尾切点? ──► 成批
                                缓冲 ≥ 15s 还没切点? ──────────► 强制硬切
                                        │
                                        ▼
                        POST /meeting_chunk (GPU)
                          返回 [{start,end,speaker,text}, ...]
                                        │
                              落库 + ws 推给前端(带说话人的句子)
                                        │
                              enhancer.on_batch(): LLM 合并调用
                                输入: 滚动纪要 + 上轮原文/修正文 + 本轮原文
                                输出: 本轮纠错文 + 上轮再修正 + 滚动纪要
                                        │ 异步执行, 结果回写库并推送
                                        │
点"结束会议" ──► _finalize(): 全场音频再送 /meeting_chunk 重跑一遍
                 = 终版(说话人标签重新标注, 即"会后版")
                 + LLM 出最终纪要/标题/事实性属性 ──► 广播给前端
```

要点：**批内用的是 GPU 一体化管线的认人；会末终版是同端点全场重跑**（不是批结果的简单拼接），所以"会后版"通常比中途批更准。

### 3.2 后端模块（server/app/）

| 文件 | 职责 |
|---|---|
| `main.py` | FastAPI 入口，挂路由，启动时初始化声纹客户端 |
| `api/ws.py` | WebSocket：音频上行（二进制 PCM）、状态/结果下行（JSON） |
| `api/meetings.py` | 会议 CRUD、详情、重放测试、重新标注 |
| `api/speakers.py` | 声纹注册/列表/删除 |
| `core/session.py` | **核心**。MeetingSession：音频缓冲、攒批调度、批次执行、会末 finalize、ws 广播；SessionManager 管多会议并发 |
| `core/gpu_pipeline.py` | GPU 服务薄客户端：`vad_ends()`（攒批切点）、`meeting_chunk()`（VAD+ASR+认人） |
| `core/enhancer.py` | LLM 增强器。每批完成后异步触发合并调用（纠错 + 上轮再修正 + 滚动纪要），超时/失败自动滚入下批补纠，不阻塞主流程 |
| `core/reannotate.py` | 会末/手动重标注：整段音频重跑认人，只换说话人标签不动文字 |
| `core/segment.py` | 句子切分工具 |
| `llm/client.py` | OpenAI 兼容客户端（base_url 指向 127.0.0.1:4000 网关），`summarize_window` / `extract_final_attributes` |
| `llm/prompts.py` | 全部提示词模板：滚动纪要、终版属性提取（事实性、AI 给啥字段渲染啥）、文字纠错、批次合并增强 |
| `db/` | SQLAlchemy + SQLite。会议表、句子表（原文/修正文/说话人/时间）、说话人表 |
| `config.py` | **所有可调参数的唯一入口**，pydantic-settings 从项目根 `.env` 读 |

### 3.3 关键配置项（config.py，改 .env 即生效，需重启后端）

| 配置 | 默认 | 含义 |

| `pipeline_batch_max_sec` | 15.0 | 超过强制硬切，防长句/长静音拖死批次 |
| `pipeline_vad_max_end_silence_ms` | 250 | VAD 判"句尾"的静音长度，**待对照实验调优** |

| `hotwords_file` / `hotwords_extra` | hotwords.txt | SeACo ASR 热词：业务词库 + 公司人名，专治专有名词听错 |

## 四、GPU 服务器部分详解（192.168.30.87）

### 4.1 diarize_svc（~/jvkit/asr/diarize_svc/service.py，FastAPI :10096）

**系统的心脏，一个"音频进、带说话人的句子出"的一体化引擎。** 端点：

| 端点 | 输入 | 输出 | 用途 |
|---|---|---|---|
| `/meeting_chunk` | wav + 阈值/热词 | `[{start,end,speaker,text}]` | 批处理与会末终版的核心。内部：归一化 → FunASR VAD 切句 → SeACo Paraformer 逐子段转写（带热词）→ ERes2NetV2 认人 |
| `/vad` | wav | 句尾时间点 | 本地后端攒批找切点用 |
| `/diarize_sent` | wav + 句子边界 | 逐句说话人 | 给定句子边界只认人（重标注底层） |
| `/embed` | wav 片段 | 声纹向量 | 注册校验 |
| `/diarize_labeled` | wav + 人数 | 聚类分人 | 实验/对比用 |

内部两个模型各司其职：

- **SeACo Paraformer**（阿里 Paraformer 热词版）：语音 → 文字。选它是因为支持热词注入，业务词、人名可以"提前告诉模型"，专治专有名词错字。
- **ERes2NetV2**（声纹）：语音片段 → 高维向量，与声纹库中已注册向量算余弦相似度，超过 `name_threshold` 才贴上人名，否则标"说话人N"。**实测比 cam++ 明显强**（早期 cam++ 在同音频上 80% 分错），这是调优过程中换过的重要决策。

声纹库 = `~/jvkit/asr/funasr-src/runtime/python/websocket/speaker_enrolls/` 下的 pcm 文件（每注册人一段）。mtime 变化自动失效重载，**不用重启服务**。

### 4.2 FunASR 服务（:10095, websocket）

历史遗留，现**只负责声纹注册/列表/删除的控制通道**，转写已不走它。注意删除声纹有个坑：`DELETE /api/speakers` 只删 FunASR 侧，ER 认人用的 pcm 文件要手动 rm（见 AGENTS.md）。

### 4.3 LLM 网关与 Langfuse

- LLM 走 `http://127.0.0.1:4000/v1`（内网 mymodule 网关，模型名 `chat`）。网关偶发抽风，所以 enhancer 的 LLM 调用设计成**失败滚入下批补纠**，永不阻塞转写主流程。
- Langfuse（localhost:3000）可选开启（`langfuse_enabled`），用于追踪每次 LLM 调用的输入输出，排查"到底是模型幻觉还是提示词问题"。

## 五、关键概念速查（教学区）

- **VAD**（语音活动检测）：判断"哪里有人说话、哪里是静音"。它的两个参数直接决定系统性格：`max_end_silence_ms` 越大，句子切得越长、漏检越多（远场小声说话被判成静音）；越小，句子越碎、句内换人被误判的概率上升。
- **DER**（说话人日志错误率）：评测分人的金标准 = (漏检 + 误报 + 混淆) / 总语音时长。比"听起来不错"客观，所有调优结论必须用 DER 说话。
- **声纹注册的同域问题**：注册音频和会议音频越像（同人、同设备、同环境），认人越准。测试里"从会议抽段注册"是最优情况，真实部署（录音笔注册、会场识别）会打折扣——这是已知边界，汇报时要讲。
- **批 vs 流式的本质**：分人模型需要上下文。流式 = 只看碎片，必错；批次 = 整段送进去，模型能看到谁接着谁说话，才是它的设计工况。

## 七、已知限制（诚实清单）

1. 非实时：批次 8~15s 延迟 + LLM 修正更慢，看不到"边说边出字"的效果。这是用延迟换正确率的主动取舍。
2. 声纹跨域未实测：注册与识别不同环境/设备时，认人率会降。
3. 未注册的说话人有概率被"坍缩"到已注册人身上（幼儿园会录声纹前全场坍缩成 admin，DER 53%）。新会场应先注册参会人声纹。
4. 远场收音是最大误差源（大房间漏检 11~15%），算法侧已近瓶颈，靠硬件（录音笔/麦克风阵列）解决。
5. LLM 网关偶发抽风；已做失败滚下批的容错，但纪要质量受网关稳定性影响。

## 第一课：图上写的文件，到底在哪？

### 1.1 先记住一个约定：图上写的是"省略前缀的相对路径"

项目根目录是 `meeting-asr/`，代码分两大阵营：

```
meeting-asr/
├── server/        # Python 后端（FastAPI）
│   └── app/       # ← 后端的"源码根"
│       ├── api/       # 对外的 HTTP/WS 接口
│       ├── core/      # 业务编排（会议怎么跑）
│       ├── llm/       # 大模型调用
│       └── db/        # 数据库表定义
└── web/           # Vue 前端
    └── src/       # ← 前端的"源码根"
        ├── components/  # 界面组件（.vue 文件）
        ├── ws/          # 和后端通信的模块（.ts 文件）
        └── ui/          # 样式、小组件
```

所以图上的写法 = 省略了"源码根"前缀：

| 图上写的 | 完整路径 |
|---|---|
| `Recorder.vue` | `web/src/components/Recorder.vue` |
| `ws/client.ts` | `web/src/ws/client.ts` |
| `ws/audio.ts` | `web/src/ws/audio.ts` |
| `api/ws.py` | `server/app/api/ws.py` |
| `core/session.py` | `server/app/core/session.py` |
| `core/enhancer.py` | `server/app/core/enhancer.py` |

**判断前端还是后端的笨办法**：`.vue` / `.ts` 一定是前端（去 `web/src/` 找）；
`.py` 一定是后端（去 `server/app/` 找）。图上"开会配置""麦克风采集"这种发生在
浏览器里的步骤，对应前端文件；"批次调度""落库"发生在服务器上，对应后端文件。

### 1.2 三种找文件的实际操作

1. **知道文件名，不知道在哪** —— VSCode 里按 `Ctrl+P`，直接输文件名
   （比如 `client.ts`），回车就打开了。这是最常用的。
2. **知道函数名，想知道在哪个文件** —— `Ctrl+Shift+F` 全局搜索
   `def meeting_chunk_3ds`（后端）或 `function start`（前端）。
3. **命令行** —— 在项目根目录：
   ```bash
   fd client.ts          # 按文件名找
   rg "def reannotate"   # 按函数名找（ripgrep）
   ```

## 第二课：这张图怎么读

### 2.1 一个节点的格式

```
┌─────────────────────────────────┐
│ 函数名() — 它在哪个文件           │  ← 加粗的是"干活的函数"
│ 入：吃进来什么                    │
│ 出：吐出去什么                    │
│ 作用：这一步为什么存在            │
└─────────────────────────────────┘
```

### 2.2 泳道（七条竖条）= 数据流经的阶段

数据从左往右流：浏览器采集 → 后端接口 → 后端编排 → GPU 算力 → LLM → 会末 → 存储。
一个会议的一生，就是数据从这七条道里"流"一遍。

### 2.3 线和箭头

- **箭头上的字** = 这一步传过去的数据（比如 `PCM 0.1s/帧`）。
- **实线** = 主链路（每场会议必经）。
- **虚线** = 辅助通路（定时任务、复用数据，不是每次都走）。
- 带流动动画的 = 最核心的音频主链路。

## 第三课：拆你问的那个节点

> **开会配置 — Recorder.vue + ws/client.ts**
> 出： WS start{title, version_mode, source_mode}

### 3.1 两个文件不是"函数位于这两文件"，而是"这一步由它俩接力完成"

这一步的完整接力是 **三棒**：

```
你在弹窗里填标题、选模式、点"开始"
  │
  │  第 1 棒：Recorder.vue（界面）
  │    你点的那个配置弹窗就是它。它把你填的东西打包，
  │    喊一嗓子 emit('start', {title, versionMode, sourceMode})
  │    （Recorder.vue:138）
  ▼
App.vue（总指挥，图上没画）
  │    接到这嗓子，转手调 client.start(...)
  ▼
  第 2 棒：ws/client.ts（通信模块）
      start() 把参数拼成一条 WebSocket 消息：
      { type:'start', title, version_mode, source_mode }
      发给后端（client.ts:36-52）
```

图上把 `App.vue` 这一棒省略了（它只是传话），所以写"Recorder.vue + ws/client.ts"。

### 3.2 顺便纠正你的猜想："前端主要是 ts 吧？"

不完全对，它俩是**分工**关系，不是主次关系：

- **`.vue` 文件 = 界面 + 交互**。里面有 HTML 模板（长什么样）、样式、
  以及一段 `<script>`（也是 TypeScript）处理点击、填表这类交互。
  你**看得到、点得到**的东西都在 `.vue` 里。
- **`.ts` 文件 = 纯逻辑模块，没有界面**。比如"怎么连 WebSocket"
  "怎么采集麦克风"这种看不见的苦力活，抽出来单独放 `.ts`，
  方便 `.vue` 调用、也方便测试。

类比：`.vue` 是柜台服务员（面对你），`.ts` 是后厨（干活不出镜）。
所以"开会配置"这一步：弹窗是 `Recorder.vue`（服务员），
把配置发给后端是 `client.ts`（后厨）。

### 3.3 那四个参数是什么意思

| 参数 | 可选值 | 决定什么 |
|---|---|---|
| `title` | 任意文字 | 会议标题。**手填了就不会被 AI 覆盖**，不填则由 AI 起 |
| `version_mode` | `live` / `final` / `both`（默认） | **跑几条管道**：live=只跑会中实时版；final=只跑会末精修版；both=两条都跑（互不纠正） |
| `source_mode` | `mic` / `online` | **声音从哪来**：mic=线下会议室，录你的麦克风；online=线上会议（腾讯会议等），录电脑系统声+你开麦时的麦克风，并且抽屏幕帧 |

## 第四课：跟着数据走一遍（一场会议的一生）

以默认模式 `both + mic` 为例，对应图上从左到右：

1. **你点"开始"** → `Recorder.vue` 发配置，`client.ts` 发 WS start。
2. **后端接单**（`api/ws.py: meeting_ws`）→ 在 MySQL `meetings` 表插一行，
   状态 `live`，然后等你喂音频。
3. **麦克风一直录**（`ws/audio.ts: MicRecorder`）→ 每 0.1 秒一小包 PCM，
   通过 WebSocket 源源不断发给后端。
4. **后端攒批**（`core/session.py: handle_audio`）→ 小包全丢进一个缓冲区
   `_audio`。每 4 秒醒一次（`_batch_loop`）：攒够 30 秒了，就调 GPU 的
   `/vad` 找"最后一句话说完了的位置"，在那里下刀切一批；
   如果 45 秒都没人停顿，就硬切（防止无限等）。
5. **降噪**（`core/preprocess.py: denoise_async`）→ 这批音频发给 GPU `/denoise`，
   GTCRN 模型把背景噪声抹掉。为什么单独一步？因为会中、会末、声纹注册
   都用同一个降噪，保证大家"听到的声音"处理一致。
6. **分人 + 转文字**（`core/gpu_pipeline.py: meeting_chunk_3ds`）→ 干两件事：
   ① `/diarize_full`：3D-Speaker 把这批音频切成段，分出"这段是甲、那段是乙"
   （匿名标签）；② `/identify_segments`：拿每段的声纹去向量库比对
   （认出"甲=冯忠俊"），同时逐段语音转文字。
7. **过滤**（`session.py` 双门槛）→ 匹配分 ≥0.50 且领先第二名 ≥0.15 才认账，
   否则标「未识别」。防止把没注册过的人硬安个名字。
8. **落库 + 上屏** → 每句话写进 `utterances` 表，同时广播给浏览器，
   你立刻看到带人名的字幕（草稿态）。
9. **每攒 4 批 = 一波，叫一次 LLM**（`core/enhancer.py: _enhance`）→
   一次调用干三件事：纠正这波的错字、订正上一波、产出这波的纪要
   （标题/要点/待办）。有屏幕帧的话先 OCR 成文字一起喂给 LLM。
10. **你点"结束"**（`stop`）→ 整段录音存盘，状态变 `ended`。
11. **后台两管道收尾**（`_finalize`）：
    - live 终版（`enhancer.finish`）：把所有波段纪要归约成一份总结；
    - final 版（`reannotate` + `run_final_pass`）：**整场录音从头重跑一遍**
      （不分批、切得更准），再按 2 分钟一窗喂 LLM，产出权威终版纪要 + 待办清单。
    两条管道互不纠正——这是设计，不是 bug。

### 换模式时哪里不一样

- `version_mode=final`：第 4~9 步整个不跑（只录音存档），结束后走第 11 步的
  final 管道。此时没有"波次"当节拍器，屏幕帧改由 120 秒定时器送 OCR
  （图上虚线 `_visual_timer_loop`）。
- `source_mode=online`：第 3 步的声音变成"系统声 + 开麦时的麦克风"，
  第 9 步多一路屏幕帧 OCR。

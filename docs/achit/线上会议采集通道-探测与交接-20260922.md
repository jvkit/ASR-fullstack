# 线上会议采集通道 — 探测结论与交接设计（2026-09-22；§3.3/3.4 已按实现后的实况更新）

> 本文档供 AI 会话交接使用：本文档所在的会话负责**音频侧**；另一个会话负责**摄像头/屏幕视觉侧**（视频内容读取）。
> 需求源头：老师要求会议纪要系统支持「线上会议」（腾讯会议）场景 + 屏幕内容（PPT/白板）监控。
> **2026-09-22 更新**：线上会议通道（系统声混音 + 屏幕抓帧 + OCR + 纪要接线）已由视觉侧
> 会话实现完毕，见 `视频侧接口与代码地图-20260922.md`（as-built）；本文档保留探测结论与设计依据。

## 1. 需求与结论速览

**线上会议通道**的工作模式一句话：

> 监听屏幕 + 系统声音，加上「我的开麦声音」（手动开关控制），三路合成一路送现有会议管线。

| 事项 | 结论 | 依据 |
|---|---|---|
| 浏览器抓系统声音 | ✅ 可行 | `web/public/probe.html` 实测：`getDisplayMedia({audio:true, video:true})` 分享整屏+勾"分享系统音频"即可拿到系统声轨 |
| 浏览器抓麦克风 | ✅ 可行（现有能力） | `getUserMedia`，生产在用 |
| 双路混音 | ✅ 可行 | GainNode 混 16k 单声道，probe.html ③ 已验证思路 |
| **自动检测腾讯会议开麦/闭麦** | ❌ **不可行** | 2026-09-22 实测（见 §2） |
| 检测进会/退会（腾讯会议占用麦克风设备） | ✅ 可行（秒级） | 同上实测 |
| 会内门控方案 | **A：前端手动开关**（用户拍板） | 不做自动门控 |
| 屏幕内容（视频侧） | 恰好同源：同一次 `getDisplayMedia` 的 video 轨 | 用户洞察：线上会议模式天然把视频需求做下来了 |

## 2. 「检测开麦」实测记录（这条路的验尸报告）

**目标**：检测用户在腾讯会议里点开/关闭麦克风（不是本页面抓麦）。

**方法**：Windows 注册表 `ConsentStore` 记录每个应用的麦克风设备占用时间。
轮询脚本：`server/scripts/mic_monitor.py`（每 1s 查 `HKCU\...\CapabilityAccessManager\ConsentStore\microphone` 下各应用的 `LastUsedTimeStart/LastUsedTimeStop`；`stop=0` = 正在使用）。日志样例 `/tmp/mic_monitor.log`（临时，未持久化）。

**结果**：
- 用户进入腾讯会议并开麦：`11:25:30 WeMeetApp.exe >>> 开始使用麦克风 (IN-USE)` —— 精确捕捉，秒级 ✅
- 用户随后**多次开麦/闭麦**：注册表 `stop` 值**全程保持 0，无任何翻转** ❌

**结论与原因**：`ConsentStore` 记录的是**应用是否持有麦克风设备句柄**。腾讯会议的"闭麦"是应用内部增益静音，**设备流从不释放**——从进会到退会只写一次 start，退会才写 stop。因此：
- 该信号语义 =「腾讯会议正在开会」（进会/退会门控，可靠）
- ≠「用户开麦中」（会内闭麦完全不可见）

其他被否掉的路（讨论过，未实现）：
- 浏览器 Web API 检测他应用占用麦克风：**不存在此 API**
- 音频相关性门控（麦克风与系统声相关→同事重复→掐掉；不相关→是我开麦）：可行但属自研算法，用户裁定不做（B 方案弃）
- 戴耳机物理隔离：可行（同事声进不了我的麦，只走系统声轨），作为使用守则推荐，不算门控

## 3. 设计：「线上会议」通道

### 3.1 前端（本会话 / 音频侧）

对现有 `web/src/ws/audio.ts`（MicRecorder）的扩展，新增 `ScreenRecorder` 或并入同一个类：

```
模式：线上会议（OnlineMeetingMode）
├── 系统声：getDisplayMedia({audio:true, video:true})
│   ├── audio 轨 → GainNode → 混音 → AudioWorklet(16k/mono/int16) → WS 上行
│   └── video 轨 → （交视频侧消费，见 §4）
├── 麦克风：getUserMedia（现有逻辑不动）
│   └── 挂一个门控 Gain（0/1），由前端开关「我开麦了」控制（方案 A）
└── 混音输出：系统声(常开) + 麦克风(开关) → 单路 16k PCM → 走现有 WS
```

关键点：
- **系统声常开、麦克风默认关**：闭麦时同事声音只从系统声轨来（不重复）；开麦说话时打开开关，自己的声音从麦克风轨来（系统声里不会有自己）。
- **戴耳机**是使用守则（防外放串音），不写代码强制。
- `getDisplayMedia` 的 video 轨**不要 stop**——即使视频侧暂时不用，停掉 video 会导致整个 display stream（含 audio）被浏览器结束。不用视觉时可以在 video 轨上单独 `track.enabled = false`。
- 弹窗必须选**「整个屏幕」+勾选「分享系统音频」**（Chrome/Edge 桌面版）；只分享标签页/窗口部分浏览器不给音频。UI 要引导用户正确勾选（探测页 probe.html 已有完整引导文案可复用）。
- 页面刷新/关闭 → display stream 断 → 线上会议通道中断。这是浏览器方案固有缺陷，接受（反正刷新也会丢 WS）。

### 3.2 后端（零改动）

- 音频路径完全复用：前端混好的单路 PCM 与现在麦克风 PCM 格式一致（16k/int16/mono），`handle_audio` → 批次管线 → GTCRN 降噪 → GPU，不动。
- 进会/退会门控（ConsentStore 轮询）：**暂不实现**。手动开关够用；真要做，`mic_monitor.py` 的 `poll()` 已封装好 powershell 读取，后端起个 1s 定时任务调它即可（但这属于锦上添花，非必需）。

### 3.3 视频侧实现（已落地，2026-09-22 视觉侧会话完成）

线上会议模式下，**同一次** `getDisplayMedia` 调用产生的 video 轨就是"屏幕内容监控"的来源。
视频链路已实现并并入主仓（详见 `视频侧接口与代码地图-20260922.md`，as-built 版）：

- 抽帧：生产用**定时抽帧**（`visual_frame_interval_sec = 10s`，canvas 缩到 960 宽），
  `web/src/ws/screen.ts`；PySceneDetect/Katna 仅作可选压缩器，非默认。
- 帧 → 多模态 LLM 出 markdown：`server/app/core/visual_ocr.py`，走内网 `new` 模型。
- 组边界信号：音频侧 enhancer 凑满一波（4 批 ≈ 2min）时调 `session.visual.take_group()`
  原子取走缓冲帧送 OCR，OCR 文本作为本波纪要 LLM 的上下文段。
- 帧上行：`POST /api/meetings/{meeting_id}/frames`，REST JSON（base64）。

| 事项 | 归属 | 状态 |

| 麦克风门控开关（方案 A，前端 UI） | 音频侧 | ✅ 已有（`Recorder.vue` 线上会议开关） |

## 5. 风险与已知限制

1. **浏览器兼容**：`getDisplayMedia` 音频抓取仅 Chrome/Edge 桌面版可靠（Firefox 不给系统音频）。公司环境如统一 Chrome 则无碍。
2. **"分享系统音频"依赖用户勾选**：忘勾 → 只有麦没有会议声。探测页/正式 UI 必须给出检测（系统声轨电平为 0 时提示）。
3. **腾讯会议必须开"系统声音外放"**：即用户不戴耳机也能外放的场景（若用户戴耳机但腾讯会议输出走耳机，系统声轨仍能抓到——`getDisplayMedia` 抓的是系统输出混音，不依赖物理外放）。⚠️ 此点需实测确认：耳机输出下系统声轨是否有信号（探测页可验证）。
4. **手动开麦开关的可靠性** = 人的自觉。忘关 → 闭麦闲聊被录（可接受，降噪+分人兜底）；忘开 → 自己的话丢失（会议纪要缺你发言，需 UI 提示）。
5. **刷新页面断流**：浏览器方案固有，接受。

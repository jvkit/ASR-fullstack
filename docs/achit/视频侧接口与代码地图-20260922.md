## 1. 协同模型（谁等谁——重要，纠正后的最终版）

**音频侧是节拍器，视频侧是从动方。** 视频侧不做自己的定时触发：

```
音频侧 L1 批次（min 30s / max 45s，VAD 句尾切点）
    → 攒满 summary_every_n_batches = 4 批 ≈ 2 分钟
    → 音频侧 enhancer._enhance() 向视频侧喊：「这是一组」
    → 视频侧把这一组期间缓冲的帧送去 OCR/多模态（吐文字）
    → OCR 文字交给音频侧 LLM → 结合出会议纪要（那边设计）
```

- **视频侧不等 LLM，视频侧等会议纪要波次**。LLM 在飞期间新帧继续缓冲（视频侧无阻塞）。
- **组边界对齐**：音频侧每凑满一波（4 批）时给视频侧发信号，视频侧把「上次信号到现在」
  缓冲的帧作为一个组送 OCR。组时长天然 = 波时长（2 分钟上下浮动），帧数 = 组时长/帧间隔。
- 视频侧**不自己计时**：波次浮动（VAD 切点）由音频侧统一裁决，视频侧只响应信号，
  避免两套时钟漂移（AGENTS.md §5 同款教训）。

## 3. 接口契约（as-built，非设计稿）

### 3.1 前端 → 后端：帧上行（已实现）

```
POST /api/meetings/{meeting_id}/frames
Content-Type: application/json
{
  "frames": [
    {"t_ms": 10230, "jpeg_b64": "..."}   # 会议内相对时间戳 ms + base64 JPEG
  ]
}
响应: {"ok": true, "accepted": 1, "buffered": 12}
```

实现位置：`server/app/api/meetings.py::meeting_frames`。

- 单请求 ≤ **6** 帧（`_MAX_FRAMES_PER_REQ`），单帧 base64 ≤ **267KB**（`_MAX_JPEG_B64`，
  即原始 JPEG ≈200KB）。超限帧被静默跳过，不 413——前端不做降质量重发。
- 会话不存在或已结束 → **404**（用 `session.stopped` 公开属性判断，不碰私有字段）。
- 前端当前是**每帧一次请求**（`screen.ts` 里 `frames: [{...}]`），契约支持攒 6 帧批量。
- 生产建议：JPEG 质量 0.8、缩略到 `visual_frame_width = 960` 宽（前端 canvas 缩略，
  **别传原图**——2546×1596 原图是 mattsvlm 慢的主因，960 宽实测小字全可读）。

### 3.2 音频侧 → 视频侧：组边界信号（进程内调用，已实现）

`server/app/core/visual_buffer.py`：

```python
class VisualBuffer:
    def __init__(self, meeting_id: str) -> None: ...
    def add_frame(self, t_ms: int, jpeg: bytes) -> bool:
        """收一帧；缓冲满（>visual_max_buffer_frames）丢最旧帧并记日志。"""
    async def take_group(self) -> list[tuple[int, bytes]]:
        """波触发时调用：原子取走缓冲的全部帧（按时间升序）；空列表=该波无帧。"""
    @property
    def buffered(self) -> int: ...
    # 观测计数：total_received / total_dropped
```

挂接点：`MeetingSession.__init__` 里 `self.visual = VisualBuffer(meeting_id)`。
触发点：`enhancer._enhance()` 取到本波音频句子之后、调 LLM 之前：

```python
ocr_text = ""
if settings.visual_enabled and self._session.visual_app:
    try:
        frames = await self._session.visual.take_group()
        if frames:
            ocr_text = await visual_ocr(frames, app=self._session.visual_app)
    except Exception:
        logger.exception("visual wave failed（不阻塞纪要）")
```

- `_enhance()` 本身是后台 task，所以这里等 OCR **不会阻塞音频采集**。
- OCR 失败返回空串，纪要按无视觉上下文继续；帧已被取走**不重试**（失败不雪球）。

### 3.3 OCR/多模态调用（as-built）

`server/app/core/visual_ocr.py`：

```python
async def visual_ocr(frames: list[tuple[int, bytes]], app: str = "") -> str
```

- 复用 `app.llm.client.client`（Langfuse 埋点同款），`model = settings.visual_llm_model`
  （默认 `"new"`；**「chat」池对图片请求报错**，2026-09-16 实测，必须用 new）。
- 帧数超 `MAX_FRAMES_PER_GROUP = 16` 时按均匀间隔抽样并**保首尾**（`_sample_frames`）。
- 每帧前插一条 `[mm:ss]` 文本标签，再插 image_url part，按时间顺序。
- 外层 `asyncio.wait_for(..., timeout=settings.visual_llm_timeout_sec)`；失败返回 `""`。
- 提示词两套模板在 `PROMPTS`：`"online"`（屏幕共享）/ `"offline"`（摄像头）；
  **模板选择是会话级**（`session.visual_app`），不是全局配置。

### 3.4 OCR 文字进纪要（拼接点，已实现）

`build_enhance_messages(ctx_summaries, prev_summary, prev_lines, cur_lines, ocr_text="")`
在最后追加一段：

```
【本波屏幕内容记录（视觉 OCR 提取，供纠错证据与纪要参考；屏幕上的术语/标题可作为纠错依据，
不要重复总结）】
{ocr_text}
```

- 纠错增益：屏幕上印着「PRIME AI」，ASR 听成「怕爱」，LLM 有证据纠正（视觉即热词库，
  热词研究失败的完美替代，2026-09-17 实测热词 λ 效果差）。
- `ocr_text` 为空（无帧/OCR 失败/线下会议）时**不拼这一段**，提示词与旧版逐字一致。
- 视觉段**不单独 append Summary**：只作上下文，纪要天然吸收屏幕信息，不新增表行。

**踩过的坑（避免重犯）**：

1. `prompts.py` 的 docstring 里不能写 `key: value` 代码式行——会被解析成注解导致
   `SyntaxError: invalid character '（'`，整个 app 起不来。已修。
2. `llm/client.py` 的 `build_enhance_messages` 是**包装函数**，`prompts.py` 改签名后
   忘了同步透传 `ocr_text` → 运行期 `TypeError`。已修。
3. `visual_ocr` 里不能写 `client.client.chat...`（重复取属性），正确的是
   `from app.llm import client as llm_client` 后 `llm_client.client.chat.completions.create`。

## 5. 配置项（已在 config.py，默认值 = 视觉侧实测结论）

```python
# ---------- 线上会议视觉通道（2026-09-22 视觉侧交接） ----------
visual_enabled: bool = True
visual_frame_interval_sec: float = 10.0   # 前端抽帧间隔（10s 甜点：写字/遮挡均覆盖）
visual_frame_width: int = 960             # 前端缩略宽度（960 实测小字全可读；白板读不清再升 1280）
visual_frame_quality: int = 80            # JPEG 质量
visual_llm_model: str = "new"             # 多模态池（chat 对图片报错，唯一可用 new）
visual_llm_timeout_sec: int = 300         # 多帧读图分钟级，给足余量
visual_prompt_app: str = "online"         # 默认模板；会话级 visual_app 优先
visual_max_buffer_frames: int = 24        # 帧缓冲上限（≈4min 积压容量，防雪球，丢了记日志）
```

`/api/config` 已返回 `visual_enabled / visual_frame_interval_sec / visual_frame_width /
visual_frame_quality`，前端 `screen.ts` 启动时读它，**不硬编码**。

**⚠️ 已知不一致**：`visual_llm_timeout_sec` 是外层 `wait_for` 的超时，但底层 OpenAI client
的 timeout 用的是共用的 `llm_timeout_sec`（默认 300）。若把 `visual_llm_timeout_sec` 调到
300 以上，底层会先超时。要真正生效需给视觉调用单独建 client。

## 6. 性能事实（做容量规划用）

| 事实 | 数值 | 来源 |
|---|---|---|
| 多模态读图（32 帧原图 2546×1596） | 221s | mattsvlm 首测 |
| 多模态读图（56 帧 960×540） | 106s（batch1）/ 336s（batch2，输出放纵逐帧小作文） | 摄像头测试 |
| 生产形状预期（12 帧 960 + 精简输出） | 30~90s（**待基准测试实锤，勿当实测**） | 推算 |
| 帧提取（55 帧 CPU） | 1~18s | imageio_ffmpeg/前端 canvas 均可 |
| 波次节奏 | 4 批 × 30~45s ≈ 2min/波 | config summary_every_n_batches |

**容量结论**：30 波/6h 会（每波一次 OCR + 一次纪要 LLM），OCR 单次 ≤90s 且与纪要 LLM
串行（先 OCR 后纪要），2min 周期下串行也够。GPU/网关侧无扩容需求。

## 8. 遗留与风险

1. **生产形状基准测试未跑**（12 帧 + 精简提示词单批耗时）——这是 §5 超时配置的直接证据，
   也是「2min 周期是否成立」的生死线。测试材料与姿势都在 `video/spike/`。
2. **浏览器真机联调未做**：抓屏、系统声混音、收帧、OCR、进纪要这条链路只在编译/构建/
   单测层面通过。`getDisplayMedia` 在 async handler 内调用通常仍被浏览器认可为用户手势，
   但需实测；分享条手动取消、网络失败等路径也需实点。
3. **真实白板手写读出未验**（摄像头测试是屏幕内容）；`offline` 模板上线前需补验。
4. **视觉文字不落库**：只出现在纪要 LLM 输入与最终 Summary 里，无独立可审计记录。
   要落库需加 schema（当前按「视觉做到出文即可」有意省略）。
5. **帧时间戳对齐**：前端 `t_ms` 用「会议开始后的相对时间」，与 `utterances.start_ms`
   同基准，拼接时天然对齐，无需换算。
6. mattsvlm 的 60s 单请求硬上限是其 app.py 的自家限制，§3.3 的直调姿势无此限制；
   但批次帧数建议 ≤16（实测 32 帧读图 2 分钟起，逼近超时），代码已强制抽样到 16。

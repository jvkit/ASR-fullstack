## 1. 协同模型（谁等谁——重要，纠正后的最终版）

**音频侧是节拍器，视频侧是从动方。** 视频侧不做自己的定时触发：

```
音频侧 L1 批次（min 30s / max 45s，VAD 句尾切点）
    → 攒满 summary_every_n_batches = 4 批 ≈ 2 分钟
    → 音频侧向视频侧喊：「这是一组」
    → 视频侧把这一组期间缓冲的帧送去 OCR/多模态（吐文字）
    → OCR 文字交给音频侧 LLM → 结合出会议纪要（那边设计）
```

- **视频侧不等 LLM，视频侧等会议纪要波次**。LLM 在飞期间新帧继续缓冲（视频侧无阻塞）。
- **组边界对齐**：音频侧每凑满一波（4 批）时给视频侧发信号，视频侧把「上次信号到现在」
  缓冲的帧作为一个组送 OCR。组时长天然 = 波时长（2 分钟上下浮动），帧数 = 组时长/帧间隔。
- 视频侧**不自己计时**：波次浮动（VAD 切点）由音频侧统一裁决，视频侧只响应信号，
  避免两套时钟漂移（AGENTS.md §5 同款教训）。

## 3. 接口契约（音频侧按此实现）

### 3.1 前端 → 后端：帧上行

**推荐 REST**（比 WS 二进制简单可靠、断线可重传；WS 已被音频二进制占用）：

```
POST /api/meetings/{meeting_id}/frames
Content-Type: application/json
{
  "frames": [
    {"t_ms": 10230, "jpeg_b64": "..."},   # 会议内相对时间戳 ms + base64 JPEG
    ...                                    # 单请求 ≤ 6 帧，前端每抽 1 帧发 1 请求亦可
  ]
}
响应: {"ok": true, "buffered": 12}
```

- JPEG 质量 0.8、缩略到 `visual_frame_width = 960` 宽（前端 canvas 缩略，**别传原图**——
  2546×1596 原图是 mattsvlm 慢的主因，960 宽实测小字全可读）。
- 单帧 ≤ 200KB；超限返回 413，前端自动降质量重发。

### 3.2 音频侧 → 视频侧：组边界信号（进程内调用，非 HTTP）

音频侧 enhancer 凑满一波时，调视频缓冲模块的**同一个会话对象**方法：

```python
# core/visual_buffer.py（音频侧新建，~60 行）
class VisualBuffer:
    """挂在 MeetingSession 上，收帧缓冲；波次触发时吐一组。"""
    def add_frame(self, t_ms: int, jpeg: bytes) -> None: ...
    async def take_group(self) -> list[tuple[int, bytes]]:
        """音频侧波触发时调用：取走缓冲的全部帧作为一个组（原子取走，防重）。
        返回 [(t_ms, jpeg), ...] 按时间升序；空组=该波无帧（纯讨论段，正常）。"""

# 挂接点：MeetingSession.__init__ 里 self.visual = VisualBuffer()
# 触发点：enhancer._enhance() 开头（LLM 调用之前）：
#   frames = await self._session.visual.take_group()
#   ocr_text = await visual_ocr(frames)          # §3.3
#   ... ocr_text 作为额外上下文拼进 build_enhance_messages 的新参数
```

### 3.3 OCR/多模态调用（视觉侧已验证的姿势）

```python
# core/visual_ocr.py（音频侧新建，~80 行）
# 网关多模态模型：base_url 同 settings.llm_base_url，model 用 "new"（1M 上下文，实测能读图）
# 「chat」池对图片请求报错（2026-09-16 实测），必须用 new。

async def visual_ocr(frames: list[tuple[int, bytes]]) -> str:
    """一组帧 → 一段 markdown 文字。失败返回 ''（调用方按无视觉上下文继续，不阻塞纪要）。"""
    client = OpenAI(base_url=settings.llm_base_url, api_key=settings.llm_api_key, timeout=300)
    content = [{"type": "text", "text": _prompt()}]
    for t_ms, jpeg in frames:
        content.append({"type": "image_url",
                        "image_url": {"url": f"data:image/jpeg;base64,{b64encode(jpeg).decode()}"}})
    resp = await asyncio.to_thread(client.chat.completions.create,
        model="new", messages=[{"role": "user", "content": content}], temperature=0.2)
    return resp.choices[0].message.content or ""
```

**提示词模板**（视觉侧拟好，落 `app/llm/prompts.py` 同款风格，视应用层无关只换文案）：

```
线上会议版（visual_online）：「以下是会议屏幕内容的定时截图（按时间顺序，间隔约10秒）。
请提取其中出现的文字信息（PPT标题/要点/白板板书/共享文档），按时间顺序输出为简洁的
markdown 记录。无新内容的重复画面跳过；不可辨认的内容标注（不可见），不要编造。」
线下会议版（visual_offline）：「以下是会议室摄像头画面截图……请描述白板/纸张上的
板书内容与人员动作，按时间顺序输出 markdown……」
```

实测依据：mattsvlm 用类似提示词在 55 帧 PPT 录屏上产出叙事级 markdown（逐页标题/要点/
翻页顺序/回翻识别），真实摄像头 960 缩略下连屏幕小字、MAC 地址都能读出。

### 3.4 OCR 文字进纪要（拼接点，音频侧设计）

建议的最小侵入拼接：`visual_ocr` 的返回文本作为**本波 LLM 的额外上下文段**：

```
【本波屏幕内容记录（OCR/视觉提取，供参考纠错与纪要）】
{ocr_text}
```

- 纠错增益：屏幕上印着「PRIME AI」，ASR 听成「怕爱」，LLM 有证据纠正（视觉即热词库，
  热词研究失败的完美替代，2026-09-17 实测热词 λ 效果差）。
- 视觉段是否独立 append 一条 Summary（title 前缀 `[视觉]`）由音频侧定；最小方案是
  只做上下文拼接（纪要天然吸收屏幕信息，不新增表行）。

```ts
const canvas = document.createElement('canvas');
canvas.width = 960; canvas.height = 540;          // 视频比例适配：h = 960 / (vw/vh)
const ctx = canvas.getContext('2d')!;
setInterval(() => {
  if (videoTrack.enabled && video.readyState >= 2) {
    ctx.drawImage(video, 0, 0, canvas.width, canvas.height);
    const jpeg = canvas.toDataURL('image/jpeg', 0.8);   // → 剥掉前缀后 POST
  }
}, 10_000);                                        // visual_frame_interval_sec
```

## 6. 性能事实（音频侧做容量规划用）

| 事实 | 数值 | 来源 |
|---|---|---|
| 多模态读图（32 帧原图 2546×1596） | 221s | mattsvlm 首测 |
| 多模态读图（56 帧 960×540） | 106s（batch1）/ 336s（batch2，输出放纵逐帧小作文） | 摄像头测试 |
| 生产形状预期（12 帧 960 + 精简输出） | 30~90s（待基准测试实锤） | 推算 |
| 帧提取（55 帧 CPU） | 1~18s | imageio_ffmpeg/前端 canvas 均可 |
| 波次节奏 | 4 批 × 30~45s ≈ 2min/波 | config summary_every_n_batches |

**容量结论**：30 波/6h 会（每波一次 OCR + 一次纪要 LLM），OCR 单次 ≤90s 且与纪要 LLM
可并发（先 OCR 后纪要串行更稳，2min 周期下串行也够）。GPU/网关侧无扩容需求。

## 7. 视觉侧遗留与风险

1. **生产形状基准测试未跑**（12 帧+精简提示词单批耗时）——建议音频侧开发前先跑，
   30 分钟内出数，这是 §5 超时配置的直接证据。测试材料与姿势都在 video/spike/。
2. **真实白板手写读出未验**（摄像头测试是屏幕内容）；线下会议提示词上线前需补验。
3. **帧时间戳对齐**：前端 t_ms 用「会议开始后的相对时间」，与 utterances.start_ms 同基准，
   拼接时天然对齐，无需换算。
4. mattsvlm 的 60s 单请求硬上限是其 app.py 的自家限制，§3.3 的直调姿势无此限制；
   但批次帧数建议 ≤16（实测 32 帧读图 2 分钟起，逼近超时）。

# 会议纪要 2.0 · 定标方案 v4（2026-09-15，"能用先"版：零自研算法）

> v3→v4 变更（用户拍板）：① **原则 = 能用手搓算法一概不碰，先上高成本简单方案，
> 优化丢后面**；② 资料上传是**会前**动作，会议总结带上这份资料；
> ③ 资料融合不用向量库（导出场景一次性使用，全量优先）；
> ④ 变化检测 v1 由 VLM 兼任（定时抽帧直送），帧差分降级为优化项。

## 〇、需求终稿（老师确认版 + 用户时序纠正）

```
会前：上传会议资料（PPT/PDF/Word，多格式解析）→ 解析文字入库，挂在会议档案上
会中：摄像头(拍PPT/白板) + 麦克风 → 传服务器：转写(带说话人) + 定时快照送 VLM → 视觉状态
会后：导出一份纪要文档 = 会议内容 + 当时画面要点 + 会前资料融合（不做问答界面）
```

## 一、算法链 v4："能用先" = 全部用现成件，只做拼装

```
音频（现有，不动）: 麦克风 → ws → 声纹区分转写 → 时间轴句子

视觉 v1（零自研）:
  摄像头 → 会场电脑浏览器定时抽帧（每 3~5s 一张 JPEG，定时器而已）
    → 直送 VLM："和当前视觉状态比，画面变了吗？变了就输出新状态"
    → PPT: 当前页 [标题/要点/文字]      白板: 板面内容状态
  VLM 兼任变化检测 —— 不做帧差分、不做图像算法，贵但零算法、当天可跑通

视觉 v2（优化，后做）: 加 pHash 帧差分，画面没变不送 VLM，调用量降一个数量级
```

**白板状态 = prompt 设计 + JSON 合并**（每轮问 VLM"和上一状态比变了什么"，增量合并），不是算法，是提示词工程。

**现成件清单**：浏览器 getUserMedia（抽帧）/ vLLM  serving 的 VLM（理解）/ python-pptx 等（资料解析）/ 现有音频管线。自研量为零，拼装胶水而已。

## 二、会前资料上传与融合（v4 重点，不用向量库）

**关键认知**：导出场景下资料只被使用**一次**（生成总结时），不需要向量数据库。

| 层级 | 触发条件 | 做法 |
|---|---|---|
| L1 全量直塞 | 资料解析文字总量 < 上下文余量（典型 30 页 PPT ≈ 5k~1.5万 token，直接塞） | 总结 prompt = 资料全文 + 转写全文，一次出，质量最好 |
| L2 按文档切块 | 单份资料超窗 | 每份资料独立先压成"结构化要点"（保留标题层级），总结时用要点+原文精选段 |
| L3（后做） | 资料超多且要问答 | 向量库——等问答需求回归再说 |

资料解析文字比直觉小一个数量级（不是扫描图像，是纯文字），"全量要命"在导出场景基本不存在；真有超窗按 L2 降级，**不做提前摘要式预处理（那是真的信息丢失）**。

## 三、⚠️ 数据安全决策点（仍开放）

云 VLM（豆包级，白板手写最强，内容出内网）vs 本地 VLM（公司供给，打印体稳、白板 decent）。D1 实测前不对外承诺白板识别率。

## 四、硬件定标（不变，D1 三连测）

摄像头 4K/关自动曝光/视场覆盖屏+白板（广角单机位 or 双机，D1 实测）；麦克风沿用 02 调研全向麦 USB。D1：PPT 屏 VLM 读出 / 手写白板 VLM 读出 / 单机位覆盖——三项全过进 W1 后续。

## 六、给老师的一句话（不变）

> 会前传资料，开会接摄像头和麦克风（会场电脑开网页），会后出纪要：谁何时说了什么、当时屏幕和白板上是什么、和会前资料的对照，一份文档带走。核心 = 多模态理解 + 时间轴对齐，本地部署，零自研算法、全现成技术拼装。

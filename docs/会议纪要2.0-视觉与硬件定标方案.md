# 会议纪要 2.0 · 视觉与硬件定标方案（2026-09-14）

> 触发：老师要求会议纪要"长眼睛"（摄像头/截屏）+ "读文件"（PPT/资料）。
> 本文档做三件事：定需求边界、定硬件、定时间安排。核心策略：**把视觉问题降级成文字问题**。

## 〇、需求纠偏（最重要的一节，先对齐认知）

老师说的形态容易被理解成"开会时让 AI 看着 PPT 写总结"——**那是错的，而且贵**。
正确的产品形态是用户自己点破的：

> **不是"对着资料给总结"，而是"结合会议 + 结合资料，任意提问"。**

"总结"只是这个系统的一次查询而已。真正的形态是：

```
问：「关于预算的讨论谁反对了？」
答：「蒋泽鹏在 10:24~10:31 反对（原话："这个成本我觉得要再压一压"），
    当时屏幕上是《Q3预算草案》第 7 页；会后补充的《预算终稿》v3 已采纳其意见。」

问：「第 3 张 PPT 讲了什么？谁讲的？」
答：「admin 在 09:47 讲到该页，要点：……」
```

这是一个 **会议知识库 + RAG 问答** 系统。这个定位直接砍掉 80% 的难度：
不需要 AI 实时"看懂"会议，只需要把会议**按时间轴切成可检索的碎片**（谁、何时、说了什么、当时屏幕是什么），问答交给检索 + 现有文本大模型。

## 二、架构定标：文字优先，视觉降级

```
┌─ 音频链路（现有）─────────────┐   ┌─ 资料采集 ─────────────────────┐
│ 麦克风 → 声纹区分转写 → 时间轴 │ + │ ①投屏电脑网页屏幕采集（首选）    │
│ 句子 [t0,t1] 谁说了什么        │   │   → 帧差分提取关键帧（翻页事件） │
└──────────────────────────────┘   │   → OCR → 该页文字（时间戳）     │
                                   │ ②摄像头拍PPT（fallback，缺陷多） │
                                   │ ③会后手动上传 PPT/PDF/Word       │
                                   └────────────────────────────────┘
                    │ 按时间轴对齐入库
                    ▼
        会议知识库：片段(说话人/文本/时间) + 幻灯片(OCR文字/时间) + 文档
                    │
                    ▼
        问答层：检索相关片段 → 现有文本大模型 → 回答（带出处）
        总结 = 一种特殊查询（map-reduce，不整窗塞）
```

**为什么这样降级是对的：**

1. **PPT 的绝大部分信息量在于文字** → OCR 就能吃到，而 OCR 是轻量模型，CPU 都能跑，**不需要 VLM**
2. **"决定这张图是否给 AI"根本不需要视觉理解** → 它只是"画面变了没有"（翻页检测）= 帧差分（pHash/SSIM），经典工程问题，零 AI
3. **"窗口爆炸"不是真问题** → 一场会几十段不该全塞一个 prompt，应该**分段索引 + 按需检索**（RAG）。窗口焦虑是架构焦虑
4. **VLM 用在 OCR 吃不掉的地方**：图表解读、流程图语义、手写白板——公司会提供多模态模型，**进计划，不砍掉**。分工：OCR 做主力（便宜、快、可审计），VLM 做语义增强与兜底

**用户建议采纳**：投屏电脑直接开我们网页传屏幕内容 > 摄像头拍 PPT。理由：像素级保真、无摩尔纹/梯形畸变/反光、与音频同一台机器天然时间同步。摄像头方案仅作为"必须拍物理白板/实物"场景的 fallback。

## 三、硬件定标

### 麦克风（沿用 02 号调研结论，按会议室档位）

| 场景 | 推荐 | 价格 | 理由 |
|---|---|---|---|
| 小会室 1-8 人 | **eMeet OfficeCore M2** | ~900-1400 | USB 零损耗、5 米 360° 拾音 |
| 中会室 8-15 人 | **eMeet M2 Max**（可两台级联） | ~1800-2800 | 级联=未来多通道雏形 |
| 大会室 15-30 人 | Poly Sync 60 / Yealink MSpeaker II | ~3500-8000 | 纯 USB 音质稳 / 政企品牌认知 |

新增约束：**若走"投屏电脑采集"方案，麦克风接投屏电脑**，与屏幕流同源同钟，时间对齐白拿。

### 摄像头：默认不买

拍 PPT 的四大缺陷：摩尔纹、梯形畸变、反光、自动曝光漂移——拍出来就是次等数据，后续所有视觉算法都在给烂输入擦屁股。屏幕采集能把这四个问题归零。
**仅当客户明确要拍物理白板/手写/实物时**再选型：4K USB 云台摄像头（如 Insta360 Link / 罗技 MX Brio）或高拍仪。列为可选项不进 MVP。

### 组合体（会议一体机）：不推荐

缺陷：镜头角度为拍人优化拍屏差、音视频管线封闭与我们系统耦合难、升级换代绑定整机。单项采购、自由组合更好。

## 四、视觉算法定标（把"要爆炸"拆成三档）

| 需求 | 实际是什么 | 难度 | 方案 |
|---|---|---|---|
| 翻页检测/关键帧 | 帧差分 | ★ 工程 | pHash/SSIM，阈值 + 防抖 |
| PPT 文字入 AI | OCR | ★ 工程 | PaddleOCR（CPU 可跑）或恢复 236.13 的 OCR 服务 |
| 关键帧"值不值得给 AI" | 语义级过滤 | ★★ AI+工程 | 先 OCR/LLM 判内容变化度，后续可换 VLM 打语义分 |
| 图表/白板/流程图理解 | 真视觉理解 | ★★★ AI | **公司提供的 VLM，进 W3~W4 计划** |

"是否给 AI"的判定逻辑 = OCR 置信度 + 内容变化度，不看图"理解"，看数"差异"。

## 五、时间安排（单人 4 周，假设硬件采购周期并行）

### W1（9/15~9/21）：定标与排雷
- [ ] **采集丢帧排查**（最高优先）：系统录音机 vs 浏览器管线录同一段，波形对比定位"一顿一顿"
- [ ] 麦克风采购+实测：接现有 replay 管线测 DER，和笔记本麦克风基线对比
- [ ] 屏幕采集技术验证：网页 getDisplayMedia 抓屏可行性 + 帧率/性能
- [ ] 确认 236.13 OCR 服务可达性；不可达则本机部署 PaddleOCR
- [ ] （并行）向老师确认需求形态：**汇报用"总结+任意提问"话术**，交付承诺分阶段

### W2（9/22~9/28）：资料链路
- [ ] 屏幕采集端：网页抓屏 → 帧差分关键帧 → 翻页时间事件
- [ ] OCR 链路：关键帧 → 文字 + 时间戳入库（slide 表）
- [ ] 时间轴对齐：slide 翻页时间 ↔ 转写句子（同机采集天然对齐，验证即可）
- [ ] 会后上传资料入口（PPT/PDF/Word 解析入库）

### W3（9/29~10/5）：问答层（核心交付）
- [ ] RAG：片段检索（时间+说话人+关键词+slide 关联）

- [ ] 整场总结 = map-reduce 特殊查询（解决"几十段超窗口"）
- [ ] VLM 接入冒烟：截图 + 提问"这页讲了什么"通链路（公司多模态模型到位即测）
- [ ] 联调一场真实会议全流程

### W4（10/6~10/12）：增强与汇报
- [ ] VLM 图表/白板/流程图理解接入正式链路（OCR 兜底）
- [ ] 端到端打磨 + 边界 case 处理
- [ ] **给老师 demo：自动总结 + 现场任意提问**（后者是记忆点）

## 六、一句话给老师（汇报话术）

> 会议纪要 2.0 = **可提问的会议知识库**。会上只管正常开麦开会，系统自动积累"谁何时说了什么、当时屏幕是什么"；会后不光出总结，还能就会议内容和补充资料**任意提问**，每个回答都带出处。摄像头方案我们用"投屏电脑直接推屏幕"替代，效果更好、成本更低。
